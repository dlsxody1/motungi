### [축3·4] 비동기 / 에러 처리
- **[요약]** 데이터 페칭 실패를 예외 throw가 아니라 **상태 union(ok/empty/error/unconfigured)으로 모델링**해, 빈 결과·설정 누락·네트워크 오류를 UI에서 각각 다른 폴백으로 분기하고 try-catch 산발을 제거.
- **[근거]** `data/opportunities.ts` `CatalogStatus`.
- **[면접 확장]** *문제*: throw 기반이면 호출부마다 try-catch 중복 + "빈 결과"와 "에러"를 구분 못 함. *결정*: 실패를 값으로 표현(errors-as-values) → UI가 상태 enum으로 선언적 분기, 로딩/빈/에러 UI 일원화. *꼬리질문 대비*: react-query의 status와 뭐가 다른가 → "카탈로그가 정적에 가까워 세션 persist로 충분, 대신 도메인 특화 상태(unconfigured=키 미설정)를 명시적으로 표현".

## 면접 3대 방어 (멘토가 갈라낸다고 한 지점)
- **"AI로 한 건가 알고 한 건가"** → ADR의 대안 비교표(A~D)로 답. "왜 안 골랐나"까지 있어야 함.
- **"문제 인식은 어디서?"** → 각 bullet의 *문제* 라인. "시켜서"가 아니라 코드 한계에서 출발.
- **"사내로 가져와 patch한 경험"** → 현재 없음. 후속으로 OSS 하나 fork/패치 내재화 서사 확보 시 별도 bullet.
