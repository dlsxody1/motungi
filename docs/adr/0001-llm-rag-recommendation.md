# ADR 0001 — 자연어 의도 기반 RAG 추천 도입

- 상태: 제안(Proposed)
- 작성일: 2026-07-09
- 맥락 문서: `docs/HANDOFF.md`, `docs/RESUME-MAPPING.md`
- 관련 코드: `packages/core/src/scoring.ts`(규칙 스코어링), `packages/core/src/diagnosis.ts`(진단), `data/opportunities.ts`(페칭)

> 이 문서의 목적은 두 가지다. (1) 실제 구현의 설계 근거를 남긴다. (2) 이력서 서사 "왜 LLM / 왜 RAG / 그 사이 의사결정 / FE가 맡은 것"의 근거가 된다. 결정은 "LLM을 붙였다"가 아니라 **"규칙 기반의 어떤 한계를 어떤 대안과 비교해 어떻게 메웠나"**로 서술한다.

---

## 1. 문제 인식 (왜 지금 규칙 기반으로 부족한가)

현재 추천은 `scoreOpportunity()`의 5축 가중합이다: fit·distance·time·difficulty·cost. 이 구조가 **구조적으로 못 하는 것**이 세 가지 있고, 그게 곧 사용자 이탈 지점이다.

1. **표현력**: 진단이 객관식 3문항(`interests`/`energy`/앵커)이라, "비 오는 날 혼자 조용히 있고 싶은데 집은 아니고" 같은 **맥락·기분**을 받을 그릇이 없다. `fit`은 `interests.includes(category)` 이진 판정이라 카테고리 enum에 안 맞는 의도는 전부 버려진다(`scoring.ts:85`).
2. **설명가능성**: `breakdown`이 `{fit:0.8, distance:0.6, ...}` 숫자로 나오지만(`scoring.ts:111`) 사용자에게 "왜 이걸 추천했는지"를 못 보여준다. 원픽 큐레이션 제품인데 신뢰의 근거가 없다.
3. **탐색성**: 사용자가 결과를 "더 실내로", "더 가까운 걸로" 자연어로 조정할 방법이 없다. 재진단(3문항 다시)밖에 없다.

→ 이 셋의 공통 원인은 **"자유로운 자연어 의도를 구조화된 검색으로 잇는 계층이 없다"**는 것.

## 2. 결정

**자연어 의도 → 구조화 → 벡터 검색(RAG) → 규칙 재랭킹 → 스트리밍 응답** 파이프라인을 추가한다. 규칙 스코어링은 **제거하지 않고 재랭킹·폴백 계층으로 유지**한다.

```
사용자 자유입력
  │  ① LLM: 의도 구조화  →  {interests?, mood, indoor?, energy?, timeWindow?, freeText}
  ▼
② pgvector: 활동 카탈로그 임베딩에서 의도 벡터로 후보 K개(예: 40) 검색   ← RAG의 R
  ▼
③ scoreOpportunity(): 후보 K개를 기존 5축으로 재랭킹 (거리·시간은 규칙이 정확)
  ▼
④ LLM: 상위 N개에 대해 breakdown 근거로 "추천 이유" 한 줄 생성        ← RAG의 G
  ▼
⑤ FE: 스트리밍 렌더 + 실패 시 순수 규칙 결과로 폴백
```

## 3. 왜 RAG인가 (단순 프롬프트 아님 — 핵심 의사결정)

"활동 목록을 프롬프트에 다 넣고 LLM더러 고르라 하면 되지 않나?"에 대한 반박이 곧 RAG의 정당성이다.

- **카탈로그가 크고 수시로 바뀐다**: 공공데이터를 pg_cron으로 매일 적재(`migrations/0007`). 전체를 컨텍스트에 넣으면 토큰 한계·비용·지연 폭발.
- **거리/시간은 LLM이 아니라 계산의 영역**: haversine 2앵커 min(`nearestAnchorKm`)·시간대 겹침(`overlapHours`)은 LLM에 맡기면 부정확하고 비싸다. → **검색(임베딩)은 의미 유사도만, 정렬(거리·시간)은 규칙**으로 역할 분리.
- 따라서: 임베딩 검색으로 **후보를 의미적으로 축소(R)**, 규칙으로 **정밀 재랭킹**, LLM은 **설명 생성(G)에만** 사용. 이게 프롬프트 스터핑 대비 정당한 이유.

## 4. 검토한 대안 (트레이드오프)

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| A. 규칙 유지 + 문항 추가 | 단순, LLM 비용 0 | 자유 자연어 못 받음. 문항 늘리면 60초 진단 UX 파괴 |
| B. 전체 카탈로그 프롬프트 스터핑 | 구현 빠름 | 토큰·비용·지연·거리 부정확. 카탈로그 커지면 붕괴 |
| C. LLM이 검색+정렬+설명 다 | 파이프라인 단순 | 거리/시간 계산을 LLM에 맡겨 부정확·고비용. 규칙 자산 폐기 |
| **D. RAG + 규칙 하이브리드 (채택)** | 검색은 의미, 정렬은 규칙, 설명은 LLM으로 역할 분리. 기존 스코어링 재활용. 폴백 확보 | 구현량 최대(임베딩 적재·벡터 인덱스·스트리밍) |

## 5. FE가 맡는 것 (이력서에서 "FE가 뭘 했나"의 답)

멘토 지적("MCP만 붙이면 되는 게 아니다") 대응 — FE가 실제로 소유하는 작업:

1. **스트리밍 UX**: 구조화 결과(①)를 편집 가능한 칩으로 즉시 렌더, 추천 이유(④)를 토큰 스트리밍으로 첫 화면 지연 은폐. (`data/opportunities.ts`의 `CatalogStatus` union에 `streaming` 상태 추가.)
2. **컨텍스트 조립**: 진단 답변 + 위치 앵커 + 자유입력을 검색 쿼리로 조립하는 클라이언트 계층. 어디까지 클라, 어디부터 Edge Function인지 경계 설계.
3. **토큰/비용 예산**: 후보 K와 설명 N 상한, 캐시(동일 의도 재요청 시 재사용), 디바운스.
4. **폴백/에러 경계**: LLM·벡터 검색 실패 시 순수 `pickTop()` 결과로 무중단 폴백. 기존 상태 union 설계와 일관.
5. **관측**: 추천 클릭률·폴백 발동률 계측 훅(재보정 근거).

## 6. 구현 스케치 (다음 단계 — 이 ADR 승인 후)

- **DB**: `pgvector` 확장, `opportunities`에 `embedding vector` 컬럼 + 적재 시 임베딩 생성(Edge Function). ivfflat/hnsw 인덱스.
- **core**: `scoreOpportunity()`는 그대로 두고, 후보를 받는 재랭킹 진입점만 노출(순수 로직 유지 = 테스트 가능성 유지).
- **Edge Function**: 의도 구조화 + 벡터 검색 + 이유 생성. 스트리밍 응답.
- **web/mobile**: 자유입력 → 스트리밍 렌더 UI, 폴백.
- **테스트**: 구조화 스키마 파싱·폴백 경로 단위테스트. E2E는 "자유입력 → 원픽" 플로우 1개.

## 7. 리스크 / 성공 기준

- 리스크: LLM 지연이 60초 진단 UX를 해칠 수 있음 → 규칙 결과를 먼저 그리고 LLM 이유를 나중에 채우는 점진 렌더로 완화.
- 리스크: 임베딩 적재 비용/신선도 → 신규·변경 활동만 증분 임베딩.
- 성공 기준(재보정용): 자유입력 사용 세션의 원픽 클릭률 ≥ 객관식 진단 세션, LLM 폴백 발동률 < 5%.

---

## 이력서 서사 압축 (이 ADR에서 뽑는 문장)

> "규칙 기반 가중합 추천이 자유로운 자연어 의도·설명가능성을 못 다루는 한계를 인식하고, 프롬프트 스터핑(토큰·거리 부정확) 대신 **pgvector RAG로 후보를 의미 검색 → 기존 규칙 스코어링으로 정밀 재랭킹 → LLM은 추천 이유 생성에만** 쓰는 하이브리드를 설계. FE에서 스트리밍 렌더·컨텍스트 조립·토큰 예산·규칙 기반 무중단 폴백을 담당."
