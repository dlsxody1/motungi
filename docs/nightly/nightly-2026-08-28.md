- **담당**: `packages/core` 순수 로직 + 테스트뿐이라 backend-impl 단독 담당(선례: core 전용 이슈는 늘 backend-impl 단독).

- **범위 확인**: `packages/core/src/store.ts`(scope 그대로) + 동일 디렉토리의 `diagnosis.ts`(scope 밖이지만 검증 유틸을 두기에 가장 자연스러운 위치 — `VALID_INTERESTS` 등 세 멤버십 집합이 이미 거기 있고 `draftToAnswers`와 짝을 이루는 콜로케이션 컨벤션을 따름). architect가 scope 확장을 검토했고, `done_when`이 "draftToAnswers류의 검증"을 명시적으로 요구하므로 신규 함수를 diagnosis.ts에 두는 것이 scope 위반이 아니라 오히려 done_when이 가리키는 위치라고 판단해 승인했다. store.ts 자체에는 새 로직을 두지 않고 diagnosis.ts의 함수를 호출만 하도록 최소화.
- **테스트 전략**: 모킹 없이 실제 `store.persist.rehydrate()`를 호출해 rehydrate 경로 자체를 태우는 방식을 architect가 요구했다 — `merge` 함수를 unit으로 직접 호출하는 것보다 실제 zustand persist 파이프라인(storage.getItem → deserialize → merge)이 통합적으로 작동함을 보장한다.
