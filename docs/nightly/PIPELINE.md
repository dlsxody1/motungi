## 핵심 규칙 (현행)

```
main   ← 사람만 승격. dev → main PR을 사람이 주기적으로 열고 머지.
 ↑
dev    ← 밤 작업의 단일 트렁크. 밤은 여기에 직접 커밋·push 한다. 브랜치·PR 없음.
```

1. **밤은 브랜치를 파지 않는다.** 매일 밤 `git fetch origin && git checkout -B dev origin/dev`
   로 최신 dev를 받아 **그 위에 직접 커밋**한다.
2. **밤은 PR을 열지 않는다.** 산출물은 `git push origin dev` 그 자체다.
3. **qa가 PUSH 게이트다.** `pnpm typecheck` + `pnpm test`가 깨끗이 통과해야만 dev에 push.
   실패 시 코드 revert, report-only 야간 노트만 push하고 STOP. **깨진 커밋은 dev에 못 간다.**
4. **계획(planner)은 최신 `origin/dev` 기준.** 어젯밤 산출물이 이미 dev에 있으므로 오늘 밤이
   같은 걸 중복 생성하지 않는다. backlog가 stale할 수 있으니 dev 실코드로 충족 여부 먼저 확인.
5. **밤은 절대 main에 손대지 않고, PR을 열거나 dev→main 승격을 하지 않는다.** 승격은 사람만.

## 0단계 — 백로그 게이트 (planner보다 먼저 판정)

밤은 시작하자마자 `docs/backlog/backlog.yml`의 `status: todo` 개수를 센다.

- **todo ≥ 2** → 위 6단계 구현 모드를 평소대로 진행한다(하룻밤 **클러스터 1개 = 1~3이슈**. 아래 "클러스터 규칙" 참조 — 옛 "하룻밤 1이슈"는 2026-08-05에 폐기).
- **todo < 2** → **그 밤은 audit 모드다. 구현하지 않고 일감을 생성한다.**
  `origin/dev` 실코드를 8축(a11y·perf·보안·타입안전·FSD 경계·테스트 커버리지·UX 패리티·데드코드)으로
  정적 감사 → 적대검증 통과분만 → `backlog.yml`에 `M-NNN`으로 등재(`status: todo`) → report-only
  야간 노트와 함께 push하고 STOP. **제품 코드는 안 건드린다.** 상세는
  `.claude/rules/workflow/nightly-pipeline.md` 0단계.

## 클러스터 규칙 (2026-08-05 신설 — 옛 "하룻밤 1이슈" 폐기)

> **왜 바뀌었나:** 8/01~8/04 나흘 연속 밤당 정확히 1건씩만 나갔다(M-039 → M-025 → M-026 → M-027).
> 리포트마다 "high 동률 N개 → tie-break로 하나"를 반복했다. todo가 19건 쌓인 시점에서
> 이 속도면 소진에 19밤이 걸린다. 병목은 백로그가 아니라 **밤당 1건 상한**이었다.

- **씨앗**: priority 최상위 todo 1개(동순위면 id 오름차순). 종전과 동일.
- **묶는 기준은 `scope` 겹침이지 priority가 아니다.** 씨앗과 실제 파일·좁은 디렉토리를 공유하는
  todo를 더한다. 같은 파일이면 겹침, `apps/mobile` ↔ `apps/mobile`은 앱 전체라 겹침이 아니다.
- **상한 3개.** 초과분은 미루고 리포트에 남긴다. 수를 채우려 낮은 priority를 끌어오지 않는다.
- **폴백 (2026-08-05 시뮬레이션에서 드러난 구멍):** 현재 todo 18건 중 9건이 `[apps/mobile]`처럼
  앱 단위 scope라 파일 겹침 판정이 불가능하다. 규칙만 바꾸면 오늘 밤 씨앗 M-030도 겹치는 게 없어
  여전히 1건짜리 밤이 된다. 그래서: **파일 겹침 후보가 0개면**(씨앗 scope에 파일이 섞여 있든 없든
  무관하다 — 기준은 *걸린 게 없다*는 사실이다) **같은 앱 + 같은 priority**인 todo를 id 오름차순
  2개까지 더한다. 예: `M-030[packages/tokens, apps/web]`은 파일 겹침 0이므로 같은 high·`apps/web`인
  `M-034`와 묶인다. 리포트에 "파일 겹침 0 → 앱 단위 폴백"이라 밝히고, 그 이슈들의 `scope`를
  실제 건드린 파일로 좁혀 백로그를 고쳐둔다(다음 밤이 제대로 묶도록).
- 폴백까지 해도 겹치는 게 없으면 1이슈 밤이며 그것도 정상 결과다.
- **왜 priority가 아니라 scope인가:** 같은 파일을 건드리는 이슈는 맥락을 공유해 한 번에 고쳐진다
  (구현자가 그 파일을 한 번만 읽는다). 반대로 "둘 다 high"라는 이유로 무관한 이슈를 묶으면
  맥락 전환만 늘고 실패 시 폭발 반경이 커진다. 예: M-045+M-046(둘 다 `saved.tsx`).

## push 규율은 이슈 단위 (같은 날 변경)
- 구현은 **이슈당 1커밋** — 독립 revert가 가능해야 한다. 클러스터를 한 커밋으로 뭉치지 않는다.
- qa 통과분만 dev로, 실패 이슈는 그 커밋만 revert하고 `todo`로 남겨 다음 밤이 재시도한다.
- **revert 후 남은 트리로 typecheck·test를 다시 돌려 green을 확인하고 push한다.** 남은 것들이
  함께 통과하지 못하면 클러스터 전체를 revert하고 report-only.
- 3건 중 2건이 나갔으면 성공이다. 미룬 것을 리포트에 명시한다.

## 왜 dev 직접 커밋(트렁크)인가
- **밤끼리 충돌 원천 차단**: 매일 같은 최신 dev 위에 쌓으므로, 어제 것을 모른 채 stale base에서
  다시 만드는 일이 없다. (오늘 M-008↔M-011 층-간 충돌 같은 게 애초에 안 생긴다.)
- **PR 더미 제거**: 밤마다 개별 draft PR이 안 생긴다. 사람은 dev→main 승격 PR **하나만** 본다.
- **main 안전판 유지**: main은 사람 승인으로만 움직인다.

## 사람이 할 일 (아침 / 주기적으로)
- `dev`의 밤 커밋을 확인 (git log origin/dev). qa 게이트를 통과한 것만 올라와 있다.
- 좋으면 **dev → main PR을 열어 승격**하고 머지. 이슈 완료 시 `docs/backlog/backlog.yml`에서
  `status: done`으로.
- dev가 오래 안 올라가면 밤들이 dev에 계속 쌓이므로, 주기적으로(주 1~2회) 승격을 권장.
